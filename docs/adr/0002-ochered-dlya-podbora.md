# ADR-0002. Асинхронный поиск водителя через очередь событий

**Дата:** 2026-11-08
**Статус:** принято

## Контекст
При создании заказа система должна подобрать ближайшего свободного водителя. Если делать это синхронно (пользователь ждет, пока сервер опросит всех водителей в базе), время ответа может вырасти до нескольких секунд, а при высоких нагрузках сервер может упасть.

## Рассмотренные варианты
1. **Синхронный вызов (REST)**. Сервер заказов напрямую обращается к Сервису подбора, ждет ответа и возвращает клиенту результат.
2. **Асинхронная передача через очередь** (RabbitMQ). Сервер заказов сохраняет заказ в БД, быстро отвечает клиенту «Заказ создан», а затем публикует событие `OrderCreated`. Сервис подбора читает это событие из очереди и ищет водителя в фоне.

## Решение
Выбран **Вариант 2**. В архитектуре (C4 Container) появился контейнер «Очередь событий», а поиск водителя вынесен в отдельный контейнер-воркер.

## Последствия
**Плюсы:** Высокая отказоустойчивость и скорость отклика для клиента. Если сервис подбора временно упадет, заказы продолжат создаваться и копиться в очереди (сообщения не потеряются), а когда сервис восстановится — он их обработает.
**Минусы:** Усложняется инфраструктура (нужен RabbitMQ). Появляется «согласованность в конечном счете» (клиент видит статус «Заказ создан», но водитель назначается через пару секунд).
**Что станет неверным, если решение пересмотреть:** Диаграмма контейнеров C4 (`02-container.puml`), динамическая диаграмма C4 (`04-dynamic.puml`), диаграмма деятельности (`process.puml`) и схема развертывания (`05-deployment.puml`).
